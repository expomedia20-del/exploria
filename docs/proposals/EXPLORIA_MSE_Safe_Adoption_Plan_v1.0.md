# برنامه پذیرش ایمن ایده‌های MSE در EXPLORIA - نسخه ۱.۰

## ۱. کنترل سند

| فیلد | مقدار |
|---|---|
| پروژه مقصد | EXPLORIA |
| منبع ایده | پروژه MSE (در مکاتبات با نام MSN نیز اشاره شده است) |
| نوع سند | پیشنهاد تصمیم و Change Candidate |
| وضعیت | **Non-Canonical / Non-Executable** |
| اثر بر Scope فعلی | ندارد |
| اثر بر کد و مدل داده فعلی | ندارد |
| مرجع حاکم در تعارض | اسناد Canonical اکسپلوریا |
| شرط اجرا | Change Request مصوب و تعیین Acceptance Criteria |

> این سند BRD، FRD، Product Backlog، Technical Design، MVP Scope Lock یا برنامه Sprint را تغییر نمی‌دهد. وجود یک مورد در این سند به معنی مجوز پیاده‌سازی آن نیست.

## ۲. هدف

هدف، استفاده انتخابی از تجربه MSE برای افزایش قابلیت سنجش، اعتماد، کنترل پاداش و توازن منافع در اکسپلوریا است؛ بدون آنکه هویت محصول، مسیر حیاتی، معماری یا دامنه MVP تغییر کند.

مسیر حیاتی قفل‌شده اکسپلوریا بدون تغییر باقی می‌ماند:

`QR Scan → PWA → OTP → Consent → Attributed Scan Event → Admin Dashboard Summary`

چرخه محصول نیز همچنان مکان‌محور و تجربه‌محور است:

`توجه → اسکن → مأموریت → پاداش → مراجعه → داده → گزارش → درآمد`

MSE در این سند فقط منبع یادگیری تطبیقی است و مرجع الزام‌آور اکسپلوریا محسوب نمی‌شود.

## ۳. تصمیم اجرایی

تصمیم فعلی سه بخش دارد:

1. اصول کم‌ریسک MSE فقط به‌عنوان کنترل تحلیلی و عملیاتی پیشنهادی نگهداری شوند.
2. هیچ قابلیت جدیدی از MSE در MVP یا Sprint 1A پیاده‌سازی نشود.
3. قابلیت‌های هم‌افزایی اقتصادی فقط پس از دریافت شواهد پایلوت و از طریق یک ماژول اختیاری برای نسخه بعد بررسی شوند.

## ۴. موارد قابل استفاده بدون تغییر دامنه محصول

موارد زیر Feature جدید محسوب نمی‌شوند و می‌توانند پس از تأیید مالک محصول در چک‌لیست‌ها، Runbookها و گزارش‌های پایلوت منعکس شوند:

| شناسه | پیشنهاد | ارزش برای اکسپلوریا | محل انطباق موجود |
|---|---|---|---|
| SAFE-01 | ثبت منبع، دوره، نسخه و کیفیت هر KPI | جلوگیری از نتیجه‌گیری با داده ناقص | PILOT / EVENT / ANALYTICS |
| SAFE-02 | امکان اعلام نتیجه «غیرقطعی» | جلوگیری از اعلام موفقیت یا شکست غیرقابل دفاع | Board Decision Gate |
| SAFE-03 | گزارش منفعت به تفکیک Venue، Merchant، Sponsor و Exploria | آشکار شدن عدم توازن هزینه و منفعت | COMM / MERCH / ANALYTICS |
| SAFE-04 | تعیین صادرکننده، تأمین‌کننده هزینه، ظرفیت و انقضای پاداش | شفافیت تعهد و کاهش اختلاف | REWARD / COMM / SUPPORT |
| SAFE-05 | توقف در کوچک‌ترین دامنه ممکن | جلوگیری از توقف کامل Venue در رخداد موضعی | PILOT / CAMPAIGN / QR / REWARD |
| SAFE-06 | ثبت علت Pause، اقدام اصلاحی و تأیید Resume | بازیابی قابل ممیزی | ADMIN / AUDIT / PILOT |
| SAFE-07 | تفکیک استحقاق پاداش از تسویه مالی | جلوگیری از تبدیل اکسپلوریا به کیف پول یا متولی وجه | REWARD / COMM |
| SAFE-08 | نمایش وضعیت‌های واقعی Pending، Rejected و Recovery | حفظ اعتماد کاربر و عملیات | UI / SUPPORT / OFFLINE |
| SAFE-09 | اجرای داخلی و Canary پیش از فعال‌سازی عمومی | کاهش ریسک پایلوت | Readiness / UAT / Pilot Runbook |

### ضابطه استفاده از SAFE-01 تا SAFE-09

- تا زمان تصویب Change Request، این موارد صرفاً پیشنهاد کنترل هستند.
- هیچ جدول، Route، Role یا Dashboard جدید صرفاً با استناد به این سند ساخته نمی‌شود.
- اگر یک پیشنهاد با Requirement موجود پوشش داده شده باشد، Requirement جدید و تکراری ایجاد نمی‌شود؛ فقط Acceptance Criteria همان Requirement می‌تواند در Change Request آینده دقیق‌تر شود.

## ۵. موارد مناسب آزمایش پس از پایلوت فعلی

این موارد ممکن است در یک آزمایش محدود با دو یا سه مقصد بررسی شوند، اما در دامنه فعلی قرار ندارند:

| شناسه | Change Candidate | شکل سازگار با اکسپلوریا | شرط ورود به آزمایش |
|---|---|---|---|
| EXP-01 | هدایت مقصد بعدی | انتقال از یک Hub یا Merchant به مقصد مکمل | وجود خط مبنا و KPI مراجعه قابل انتساب |
| EXP-02 | مأموریت مشارکتی | Quest زنجیره‌ای میان چند مقصد داخل یک Venue | تأیید Venue و Merchantها، ظرفیت و پاداش روشن |
| EXP-03 | گزارش توازن منفعت | مقایسه مشارکت، هزینه و منفعت هر ذی‌نفع | داده کافی و تعریف مصوب ارزش |
| EXP-04 | بودجه‌بندی ساده پاداش | سقف تعهد کمپین بدون نگهداری وجه | تعیین Cost Owner و قرارداد معتبر |
| EXP-05 | Attribution چندمرحله‌ای | Media → Scan → Mission → Visit → Redemption | Event lineage معتبر و Quality Flag |

قواعد آزمایش:

- فقط در یک Venue و با Feature Flag خاموش به‌صورت پیش‌فرض؛
- بدون کیف پول، نگهداری وجه یا پرداخت داخلی؛
- بدون تغییر مسیر حیاتی کاربران غیرعضو آزمایش؛
- با امکان توقف مستقل و بازگشت به رفتار فعلی؛
- با گزارش Go / Iterate / Pivot / Stop؛
- با حفظ حریم داده و دسترسی محدود Merchant و Sponsor.

## ۶. موارد قرنطینه‌شده برای نسخه دوم

موارد زیر تا پیش از تصویب رسمی نسخه دوم **Out of Scope** هستند:

- Journey Graph عمومی و Directed Edge قابل مدیریت میان همه مقصدها؛
- Reward Pool مشترک میان چند کسب‌وکار یا Venue؛
- رزرو مالی و Value Ledger پیشرفته؛
- Settlement Engine و تطبیق مالی خودکار؛
- کیف پول، نگهداری وجه یا درگاه پرداخت داخلی؛
- وفاداری مشترک چندمکانی؛
- Next Best Offer و شخصی‌سازی الگوریتمی؛
- Marketplace قرارداد یا تبادل ارزش؛
- معماری Microservice یا Event-driven سنگین برای قابلیت‌های هم‌افزایی.

عنوان مفهومی پیشنهادی برای بررسی آینده:

**Exploria 2.0 - Ecosystem Synergy Layer**

این عنوان فقط یک نام برنامه‌ریزی است و اعلام نسخه محصول یا تعهد تحویل محسوب نمی‌شود.

## ۷. مرز معماری پیشنهادی برای آینده

اگر EXP-01 تا EXP-05 در پایلوت ارزش خود را اثبات کنند، توسعه باید در همان Laravel + React Modular Monolith و به‌صورت یک مرز دامنه اختیاری انجام شود:

```text
هسته فعلی EXPLORIA
├── Venue / Zone / Hub / Touchpoint
├── Campaign / Quest
├── QR / Event
├── Reward / Merchant
└── Analytics / Pilot / Support

مرز اختیاری آینده: SYNERGY
├── Journey Transition
├── Hub/Merchant Edge
├── Funding Policy
├── Benefit Balance
└── Value Evidence Ledger
```

اصول این مرز:

- هسته فعلی به SYNERGY وابستگی اجباری نداشته باشد.
- SYNERGY از Entityهای موجود با شناسه و Contract مشخص استفاده کند و آن‌ها را جایگزین نکند.
- Business Logic در Laravel Service/Action باقی بماند.
- React فقط UI و State رابط را مدیریت کند.
- هیچ Package سنگین یا سرویس مستقل بدون تصمیم معماری مصوب اضافه نشود.
- Migrationها افزایشی، قابل بازگشت و سازگار با داده موجود باشند.

## ۹. Gateهای لازم پیش از هر پیاده‌سازی

هر Change Candidate آینده باید همه Gateهای زیر را بگذراند:

1. **Problem Evidence Gate:** مسئله در پایلوت اکسپلوریا با داده یا شواهد عملیاتی مشاهده شده باشد.
2. **Canonical Trace Gate:** ارتباط آن با BRD، FRD، CPL و Backlog مشخص باشد.
3. **Scope Gate:** Product Owner اثر Scope و اولویت را تصویب کند.
4. **Economic Gate:** مالک هزینه، منفعت مورد انتظار و معیار توقف مشخص باشد.
5. **Legal and Privacy Gate:** رضایت، حقوق پاداش، داده و مسئولیت طرف‌ها تعیین شود.
6. **Architecture Gate:** عدم تغییر معماری و عدم وابستگی اجباری هسته تأیید شود.
7. **Pilot Gate:** اجرای محدود، Feature Flag، Rollback و سناریوی Recovery وجود داشته باشد.
8. **Verification Gate:** تست Backend/Frontend، Authorization، Audit و UAT تعریف شده باشد.

عدم عبور از هر Gate به معنی توقف Change Candidate است.

## ۱۰. معیار پذیرش برنامه ایمن

این برنامه فقط زمانی درست رعایت شده است که:

- مسیر حیاتی و رفتار فعلی اکسپلوریا بدون تغییر باقی بماند؛
- هیچ قابلیت MSE بدون Change Request وارد کد یا Backlog Canonical نشود؛
- قابلیت‌های مالی پیشرفته در Sprint 1A پیاده‌سازی نشوند؛
- MSE جایگزین BRD یا FRD اکسپلوریا نشود؛
- هر آزمایش آینده محدود، قابل خاموش‌کردن و قابل بازگشت باشد؛
- نتیجه آزمایش با خط مبنا و کیفیت داده گزارش شود؛
- در نبود شواهد کافی، نتیجه «غیرقطعی» ثبت شود؛
- حقوق کاربر، Merchant، Sponsor و Venue در توقف یا پایان آزمایش روشن باشد.

## ۱۲. نتیجه

در وضعیت فعلی، بهترین ارتقای اکسپلوریا «افزودن Featureهای MSE» نیست؛ بلکه استفاده از اصول آن برای دقیق‌تر شدن سنجش، مسئولیت پاداش، بازیابی عملیات و توازن منفعت است. قابلیت‌های واقعی هم‌افزایی تنها پس از اثبات مسئله در پایلوت، تصویب Change Request و در قالب یک مرز اختیاری قابل بررسی هستند.
